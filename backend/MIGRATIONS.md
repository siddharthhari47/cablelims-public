# Database migrations

CableLIMS uses [Alembic](https://alembic.sqlalchemy.org/) to manage the SQLite schema.
This replaced an older mechanism (`app/db_migrate.py`'s original `sync_schema()`) that
introspected the live database on every startup and issued raw `ALTER TABLE ... ADD COLUMN`
statements for anything the ORM models declared that the file didn't have yet. That worked, but
every change it made was silent and untracked — there was no record of what schema version a
given database was actually at, and no way to review a schema change before it ran against
someone's live data.

## How it works now

- **`backend/alembic/`** holds the migration environment (`env.py`) and every migration script,
  in `backend/alembic/versions/`.
- **`backend/alembic.ini`** is Alembic's config file. Its `sqlalchemy.url` is a placeholder —
  `alembic/env.py` always overrides it with the app's real database path from `app.db`, so a
  bare `alembic upgrade head` run from a terminal always targets the actual `backend/data/`
  database, never a stale hardcoded one.
- **`app/db_migrate.py`** is what the running application actually calls, once, at startup (see
  `app/main.py`). `run_migrations(engine)`:
  1. Checks whether this is a **pre-Alembic database** — one that already has a full schema
     (built by the old `create_all()` + `sync_schema()` pair every install before this change
     used) but no `alembic_version` table. If so, it **stamps** the database at the baseline
     revision (`69eb6322f401`) rather than replaying it — stamping just records "this database's
     schema already matches this revision," which is true by construction (the baseline
     migration was generated by autogenerating against an empty database, so it reproduces
     exactly what `create_all()` used to build).
  2. Runs `alembic upgrade head`, applying any migrations newer than the database's current
     stamped revision. On an already-up-to-date database this is a fast no-op.

This keeps the deployment model exactly what it was before: an operator double-clicks
`start_cablelims.bat`, and schema updates happen automatically, with no command line involved.
What changed is that every schema change is now a specific, numbered, reviewable Python file
under version control, and the database records which ones it has actually applied.

## Writing a new migration

When a model in `app/models/models.py` changes:

```bash
cd backend
venv\Scripts\python -m alembic revision --autogenerate -m "short description"
```

This diffs `Base.metadata` (every ORM-declared table) against the actual database at
`backend/data/cablelims.db` and writes a new file into `alembic/versions/`. **Always read the
generated file before committing it** — autogenerate is a good first draft, not a guarantee:

- SQLite can't `ALTER COLUMN`, `DROP COLUMN`, or add most constraints in place. `env.py` already
  configures `render_as_batch=True`, so Alembic emits *batch* operations (recreate table, copy
  rows, drop old, rename) for these automatically — but batch mode can still get column
  defaults, nullability, or index names wrong on a genuinely complex change. Check the generated
  SQL makes sense for SQLite specifically, not just "looks like a reasonable diff."
- Only additive, backward-compatible changes should ship in a single migration wherever
  possible, matching the constraint the old `sync_schema()` operated under (nullable-or-defaulted
  new columns, not renames — a rename is a drop-and-add to anyone still reading the old column
  name, which is a bigger, more deliberate change than routine schema evolution should be).
- Write the `downgrade()` too, even though nothing in this app's deployment currently calls it —
  it's cheap insurance and documents the reverse operation for whoever reads this file later.

Test the migration before shipping it:

```bash
venv\Scripts\python -m alembic upgrade head    # apply it to your local dev database
venv\Scripts\python -m alembic downgrade -1    # confirm downgrade() actually works
venv\Scripts\python -m alembic upgrade head    # back to head
```

`tests/test_migrations.py` covers `run_migrations()` itself (fresh-database bootstrap,
pre-Alembic stamping, and a regression test for a real bug this feature found — Alembic's own
`fileConfig()` call silently disabling the app's logger unless told not to). It does not need to
change when you add an ordinary new migration; it tests the mechanism, not any specific schema.

## Useful commands

```bash
venv\Scripts\python -m alembic current     # what revision is this database stamped at?
venv\Scripts\python -m alembic history     # full migration chain
venv\Scripts\python -m alembic upgrade head  # apply pending migrations manually
```
